# 個人記帳本資料庫設計說明書

本文件為個人專屬記帳系統（運行於 Supabase PostgreSQL）之資料表設計規範。系統由後續之 Flask 與 SQLAlchemy 後端讀寫，此階段僅定義資料結構與完整商業邏輯約束，不包含任何程式碼實作。

---

## 1. 設計總覽與核心架構原則

本系統圍繞個人四大財務冊子展開：**入帳**、**花費**、**投資**、**發票**，所有資金變動最終歸結於**帳戶**。

### 1.1 資料型態與命名慣例
- **命名規則**：所有資料表名稱與欄位名稱均採用小寫英文，單字之間以底線（`snake_case`）分隔。
- **主鍵規範**：每張表皆使用資料庫自動遞增產生、建立後不允許變更之整數主鍵（PostgreSQL 之 `BIGINT GENERATED ALWAYS AS IDENTITY`）。
- **金額與數值**：金額與股數皆使用具備小數精度之數值型態（PostgreSQL 之 `NUMERIC`），禁止使用浮點數（`FLOAT` / `REAL`）以避免進位誤差。
- **幣別格式**：採用國際標準 ISO 4217 之三碼大寫英文字元（如 `TWD`、`USD`、`JPY`）。
- **時間格式**：所有時間欄位一律採用帶時區之時間戳記（PostgreSQL 之 `TIMESTAMPTZ`）。
- **審計時間戳記**：
  - `created_at`：於資料列插入時由資料庫預設填入當前 UTC 時間（`DEFAULT (now() AT TIME ZONE 'utc')`）。
  - `updated_at`：由應用程式（API）於每次更新資料列時主動填入當前 UTC 時間。

### 1.2 外鍵參照與刪除規則
- **預設保護**：所有外鍵關聯皆採用「RESTRICT」（或 NO ACTION），當父列仍被任何子列參照時，嚴格禁止刪除父列。
- **唯一例外**：發票品項明細表（`invoice_item`）對統一發票主表（`invoice`）之外鍵參照採用「CASCADE」，發票刪除時，其所屬品項明細隨同發票一併消失。

### 1.3 匯率與外幣基準
- 系統內部以新台幣（TWD）為基準幣別。
- 凡涉及金額之記錄列（入帳、花費、移轉、投資交易、發票），皆強制記錄該筆交易之幣別（`currency`）以及換算為新台幣之匯率（`exchange_rate_to_twd`）。
- 當幣別為 `TWD` 時，`exchange_rate_to_twd` 強制固定為 `1.0`；外幣則必須大於 `0`。

## 2. 資料表詳細設計

系統共規劃 11 張實體資料表：
1. `account`（帳戶表）
2. `income_category`（入帳分類表）
3. `expense_category`（花費分類表）
4. `income`（入帳表）
5. `expense`（花費表）
6. `transfer`（帳戶移轉表）
7. `investment_target`（投資標的表）
8. `investment_transaction`（投資交易表）
9. `invoice`（統一發票表）
10. `invoice_item`（發票品項明細表）
11. `invoice_lottery_prize`（開獎獎項與中獎號碼表）

---

### 2.1 帳戶表（`account`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄個人持有的所有金融容器，包括現金錢包、銀行活存/定存帳戶、信用卡、證券交割戶。
- **單獨成表原因**：錢必須落在實體或虛擬帳戶上。帳戶具備獨立的金融屬性（帳戶名稱、機構、幣別、類型），將帳戶獨立成表可作為所有資金流動（入帳、花費、移轉、投資交割）的錨點，確保資金來源與去向清晰。

#### 欄位清單
| 欄位名稱 | 形態說明 | 必填 / 可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 整數主鍵 | 必填 | 不能重複 | 資料庫產生，建立後不改 |
| `name` | 文字 | 必填 | 不能重複 | 帳戶名稱（如「台新活存」、「玉山信用卡」） |
| `account_type` | 文字 | 必填 | 可重複 | 帳戶型態：`cash`、`bank`、`credit_card`、`brokerage_settlement` |
| `currency` | CHAR(3) | 必填 | 可重複 | 該帳戶計價幣別（如 `TWD`、`USD`） |
| `initial_balance` | 數值（含小數） | 必填 | 可重複 | 開戶/啟用時之起始餘額，預設 0 |
| `institution_name` | 文字 | 可空 | 可重複 | 金融機構名稱（如「台新銀行」） |
| `account_number` | 文字 | 可空 | 可重複 | 銀行或卡號末四碼，供識別 |
| `description` | 文字 | 可空 | 可重複 | 帳戶備註說明 |
| `created_at` | TIMESTAMPTZ | 必填 | 可重複 | 建立時間，資料庫預設填入 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 可重複 | 更新時間，由 API 寫入 UTC |

#### 主鍵、外鍵與約束規範
- **主鍵**：`id`
- **外鍵**：無
- **PostgreSQL 約束**：
  - `UNIQUE (name)`：帳戶名稱全域不重複。
  - `CHECK (account_type IN ('cash', 'bank', 'credit_card', 'brokerage_settlement'))`：限制合法帳戶型態。
  - `CHECK (char_length(currency) = 3)`：幣別固定為 3 碼。
- **API 檢查規範**：無。

### 2.4 入帳表（`income`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄所有使個人資產實質增加的金流事件（薪水入帳、存款利息、商家退款、發票中獎獎金、投資現金股利、減資退回現金）。
- **單獨成表原因**：入帳代表淨資產的正向增加，是財務收支核心事實之一。透過獨立成表，能夠完整追蹤每筆款項進入的帳戶、幣別、匯率，以及可選擇性追溯至發票中獎或投資交易事件。

#### 欄位清單
| 欄位名稱 | 形態說明 | 必填 / 可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 整數主鍵 | 必填 | 不能重複 | 資料庫產生，建立後不改 |
| `account_id` | 整數外鍵 | 必填 | 可重複 | 指向入款之 `account.id` |
| `category_id` | 整數外鍵 | 必填 | 可重複 | 指向 `income_category.id` |
| `amount` | 數值（含小數） | 必填 | 可重複 | 入帳金額，必須大於 0 |
| `currency` | CHAR(3) | 必填 | 可重複 | 入帳幣別 |
| `exchange_rate_to_twd` | 數值（含小數） | 必填 | 可重複 | 換算為台幣之匯率（台幣固定為 1.0） |
| `received_at` | TIMESTAMPTZ | 必填 | 可重複 | 實際入帳時間點 |
| `invoice_id` | 整數外鍵 | 可空 | 不能重複 | 關聯中獎發票之 `invoice.id`（一張發票最多一筆） |
| `investment_transaction_id`| 整數外鍵 | 可空 | 不能重複 | 關聯投資交易之 `investment_transaction.id`（一筆交易最多一筆） |
| `note` | 文字 | 可空 | 可重複 | 入帳事由與備註 |
| `created_at` | TIMESTAMPTZ | 必填 | 可重複 | 建立時間，資料庫預設填入 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 可重複 | 更新時間，由 API 寫入 UTC |

#### 主鍵、外鍵與約束規範
- **主鍵**：`id`
- **外鍵**：
  - `account_id REFERENCES account(id) ON DELETE RESTRICT`
  - `category_id REFERENCES income_category(id) ON DELETE RESTRICT`
  - `invoice_id REFERENCES invoice(id) ON DELETE RESTRICT`
  - `investment_transaction_id REFERENCES investment_transaction(id) ON DELETE RESTRICT`
- **PostgreSQL 約束**：
  - `CHECK (amount > 0)`：入帳金額必大於 0。
  - `CHECK ((currency = 'TWD' AND exchange_rate_to_twd = 1.0) OR (currency != 'TWD' AND exchange_rate_to_twd > 0))`：台幣匯率固定為 1，外幣匯率大於 0。
  - `UNIQUE (invoice_id)`：發票一旦關聯入帳，同一張發票至多只能有一筆入帳（NULL 列不互斥）。
  - `UNIQUE (investment_transaction_id)`：投資交易一旦關聯入帳，同一筆交易至多只能有一筆入帳（NULL 列不互斥）。
  - `CHECK (NOT (invoice_id IS NOT NULL AND investment_transaction_id IS NOT NULL))`：同一筆入帳不得同時來自發票與投資交易。
- **API 檢查規範**：
  - 若指定 `invoice_id`，API 需確認該發票對獎狀態確為中獎，且入帳金額等於中獎獎金。
  - 若指定 `investment_transaction_id`，API 需確認該投資交易之類型為現金股利（`cash_dividend`）或減資（`capital_reduction`）。

### 2.5 花費表（`expense`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄所有個人資金流出與消費行為。特別支援消費日（`spent_at`）與扣款日（`settled_at`）分離之場景（如信用卡消費當日入單，下月扣款）。
- **單獨成表原因**：花費為個人淨資產減少之主要來源。單獨成表可支援一張發票對應多筆花費（品項分攤或分筆支出），並獨立追蹤扣款帳戶與消費時間維度。

#### 欄位清單
| 欄位名稱 | 形態說明 | 必填 / 可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 整數主鍵 | 必填 | 不能重複 | 資料庫產生，建立後不改 |
| `account_id` | 整數外鍵 | 必填 | 可重複 | 指向扣款/掛帳帳戶 `account.id` |
| `category_id` | 整數外鍵 | 必填 | 可重複 | 指向 `expense_category.id` |
| `invoice_id` | 整數外鍵 | 可空 | 可重複 | 關聯統一發票 `invoice.id`（一張發票可對多筆花費） |
| `amount` | 數值（含小數） | 必填 | 可重複 | 花費金額，必須大於 0 |
| `currency` | CHAR(3) | 必填 | 可重複 | 花費幣別 |
| `exchange_rate_to_twd` | 數值（含小數） | 必填 | 可重複 | 換算為台幣之匯率（台幣固定為 1.0） |
| `spent_at` | TIMESTAMPTZ | 必填 | 可重複 | 實際消費發生時間（如刷卡日） |
| `settled_at` | TIMESTAMPTZ | 可空 | 可重複 | 實際從帳戶扣款/結算時間（如信用卡帳單扣款日，現金消費可同 `spent_at`） |
| `merchant` | 文字 | 可空 | 可重複 | 消費商家名稱 |
| `note` | 文字 | 可空 | 可重複 | 消費備註說明 |
| `created_at` | TIMESTAMPTZ | 必填 | 可重複 | 建立時間，資料庫預設填入 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 可重複 | 更新時間，由 API 寫入 UTC |

#### 主鍵、外鍵與約束規範
- **主鍵**：`id`
- **外鍵**：
  - `account_id REFERENCES account(id) ON DELETE RESTRICT`
  - `category_id REFERENCES expense_category(id) ON DELETE RESTRICT`
  - `invoice_id REFERENCES invoice(id) ON DELETE RESTRICT`（父列發票被花費參照時禁止刪除）
- **PostgreSQL 約束**：
  - `CHECK (amount > 0)`：花費金額必大於 0。
  - `CHECK ((currency = 'TWD' AND exchange_rate_to_twd = 1.0) OR (currency != 'TWD' AND exchange_rate_to_twd > 0))`：台幣匯率固定為 1，外幣匯率大於 0。
- **API 檢查規範**：
  - 一張發票可對應多筆花費，API 寫入時**不強制**花費合計需等於發票總額（允許發票中部分品項報帳或自留差額）。

### 2.6 帳戶移轉表（`transfer`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄個人在自身不同金融帳戶之間的資金搬移（例如：從銀行提領現金、銀行轉帳至券商交割戶、銀行扣款繳納信用卡費）。
- **單獨成表原因**：移轉不改變個人整體淨資產，既非收入也非花費。若將其拆成一筆花費與一筆入帳，將嚴重扭曲收支與損益報表。單獨成表能以單一列完整表彰轉出與轉入端，並原子化維持資金守恆。

#### 欄位清單
| 欄位名稱 | 形態說明 | 必填 / 可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 整數主鍵 | 必填 | 不能重複 | 資料庫產生，建立後不改 |
| `from_account_id` | 整數外鍵 | 必填 | 可重複 | 轉出帳戶，指向 `account.id` |
| `to_account_id` | 整數外鍵 | 必填 | 可重複 | 轉入帳戶，指向 `account.id` |
| `from_amount` | 數值（含小數） | 必填 | 可重複 | 轉出金額（轉出帳戶幣別），必須大於 0 |
| `to_amount` | 數值（含小數） | 必填 | 可重複 | 轉入金額（轉入帳戶幣別），必須大於 0 |
| `currency` | CHAR(3) | 必填 | 可重複 | 基準幣別（通常為轉出帳戶幣別） |
| `exchange_rate_to_twd` | 數值（含小數） | 必填 | 可重複 | 轉出幣別換算為台幣之匯率（台幣固定為 1.0） |
| `transferred_at` | TIMESTAMPTZ | 必填 | 可重複 | 轉帳執行時間 |
| `note` | 文字 | 可空 | 可重複 | 移轉備註（如「繳納玉山卡費」） |
| `created_at` | TIMESTAMPTZ | 必填 | 可重複 | 建立時間，資料庫預設填入 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 可重複 | 更新時間，由 API 寫入 UTC |

#### 主鍵、外鍵與約束規範
- **主鍵**：`id`
- **外鍵**：
  - `from_account_id REFERENCES account(id) ON DELETE RESTRICT`
  - `to_account_id REFERENCES account(id) ON DELETE RESTRICT`
- **PostgreSQL 約束**：
  - `CHECK (from_account_id != to_account_id)`：禁止轉入與轉出為同一帳戶。
  - `CHECK (from_amount > 0 AND to_amount > 0)`：轉出與轉入金額均需大於 0。
  - `CHECK ((currency = 'TWD' AND exchange_rate_to_twd = 1.0) OR (currency != 'TWD' AND exchange_rate_to_twd > 0))`：台幣匯率約束。
- **API 檢查規範**：
  - 若兩帳戶為同幣別，API 寫入前需檢查 `from_amount` 與 `to_amount` 是否相等（若有轉帳手續費，手續費應另記一筆 `expense`）。

### 2.7 投資標的表（`investment_target`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄投資標的靜態資訊，包含股票代號、標的名稱、所屬市場別（台股、美股）及交易幣別。
- **單獨成表原因**：每一檔標的具備唯一識別性。若將標的名稱直接填入交易紀錄，會產生大量冗餘且難以進行名稱異動維護。獨立成表後，可作為交易明細的外鍵主體，並以標的為維度計算持有股數與平均成本。

#### 欄位清單
| 欄位名稱 | 形態說明 | 必填 / 可空 | 唯一性 | 說明 |

### 2.8 投資交易表（`investment_transaction`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄所有針對投資標的進行之異動交易事件，涵蓋：買進、賣出、現金股利、配股、股息再投入、分割、合併、減資。
- **單獨成表原因**：投資交易是證券資產生命週期的流水帳。每筆交易具有交易類別、成交股數、單價、費用與交割金流，持有股數與成本均由歷史交易推導，單獨成表為精準追蹤持股狀態之必要設計。

#### 欄位清單
| 欄位名稱 | 形態說明 | 必填 / 可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 整數主鍵 | 必填 | 不能重複 | 資料庫產生，建立後不改 |
| `target_id` | 整數外鍵 | 必填 | 可重複 | 指向 `investment_target.id` |
| `transaction_type` | 文字 | 必填 | 可重複 | 交易類別（見下方列舉） |
| `transacted_at` | TIMESTAMPTZ | 必填 | 可重複 | 交易成交/生效時間 |
| `shares` | 數值（含小數） | 必填 | 可重複 | 交易股數（支援小數股；現金股利為 0） |
| `price_per_share` | 數值（含小數） | 可空 | 可重複 | 每股單價（買進/賣出/再投入必填；其餘可空） |
| `fee` | 數值（含小數） | 必填 | 可重複 | 手續費與交易稅，預設 0 |
| `settlement_amount` | 數值（含小數） | 必填 | 可重複 | 淨交割金額（買進為付費總額，賣出為入帳總額，無金流則為 0） |
| `settlement_account_id` | 整數外鍵 | 可空 | 可重複 | 交割扣款/入款帳戶 `account.id`（無直接扣款時為空） |
| `currency` | CHAR(3) | 必填 | 可重複 | 交易幣別 |
| `exchange_rate_to_twd` | 數值（含小數） | 必填 | 可重複 | 換算為台幣之匯率（台幣固定為 1.0） |
| `ratio` | 數值（含小數） | 可空 | 可重複 | 分割/合併/減資比例（如 1 拆 2 記 2.0，2 併 1 記 0.5） |
| `note` | 文字 | 可空 | 可重複 | 交易備註 |
| `created_at` | TIMESTAMPTZ | 必填 | 可重複 | 建立時間，資料庫預設填入 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 可重複 | 更新時間，由 API 寫入 UTC |

#### 交易種類（`transaction_type`）列舉值
1. `buy`：買進。股數增加，從交割戶扣款。
2. `sell`：賣出。股數減少，款項入交割戶。
3. `cash_dividend`：現金股利。股數不變，發放現金（連動一筆 `income`）。
4. `stock_dividend`：配股（股票股利）。股數增加，無交割金流。
5. `reinvest`：股息再投入。股數增加，股利直接買入新股數。
6. `split`：股票分割。股數依比例增加，單價依比例降低，成本不變。
7. `reverse_split`：股票合併。股數依比例減少，單價依比例提升，成本不變。
8. `capital_reduction`：減資。股數減少；若退回現金，退回款項連動一筆 `income`。

#### 主鍵、外鍵與約束規範
- **主鍵**：`id`
- **外鍵**：
  - `target_id REFERENCES investment_target(id) ON DELETE RESTRICT`
  - `settlement_account_id REFERENCES account(id) ON DELETE RESTRICT`
- **PostgreSQL 約束**：
  - `CHECK (transaction_type IN ('buy', 'sell', 'cash_dividend', 'stock_dividend', 'reinvest', 'split', 'reverse_split', 'capital_reduction'))`
  - `CHECK (shares >= 0)`：股數字段一律記正值。
  - `CHECK (fee >= 0)`：費用不可為負值。
  - `CHECK (settlement_amount >= 0)`：交割金額記正值。
  - `CHECK ((currency = 'TWD' AND exchange_rate_to_twd = 1.0) OR (currency != 'TWD' AND exchange_rate_to_twd > 0))`：台幣匯率約束。
- **API 檢查規範**：
  - **賣出不得使持有股數小於 0（由 API 在寫入前檢查）**：在寫入 `sell` 交易前，API 必須於資料庫交易內鎖定該標的，累加該交易時間點前之所有交易獲得有效持股數；若本次賣出股數大於目前持有股數，API 必須拒絕寫入。
  - 現金股利或減資退還現金若產生實質金流，API 在寫入時可引導產生或關聯至一筆 `income`（`income.investment_transaction_id` 指向本筆交易），由入帳表記錄款項進入之帳戶。

### 2.9 統一發票表（`invoice`）

#### 記載內容與單獨成表原因
- **記載內容**：記錄台灣統一發票主體，包含開立日期、發票字軌號碼（2 碼大寫英文字母 + 8 碼數字）、買賣方統一編號、發票總金額及開獎期別。

## 3. 餘額與持有股數之計算邏輯（非實體可修改欄位）

依照設計原則，**帳戶餘額（Balance）與投資持有股數（Shares Held）一律不做成可修改的欄位**，避免並行更新偏差或人為篡改，皆由歷史資料列即時彙整計算。

### 3.1 帳戶餘額推導邏輯
指定帳戶（`account_id = :acc_id`）之當前餘額，由以下各資料表之關聯列加減算出：

$$\begin{aligned}
\text{帳戶當前餘額} = &\ \text{account.initial\_balance} \\
&+ \sum \text{income.amount} \quad (\text{條件: } \text{account\_id} = :acc\_id) \\
&- \sum \text{expense.amount} \quad (\text{條件: } \text{account\_id} = :acc\_id \text{ 且已扣款}) \\
&+ \sum \text{transfer.to\_amount} \quad (\text{條件: } \text{to\_account\_id} = :acc\_id) \\
&- \sum \text{transfer.from\_amount} \quad (\text{條件: } \text{from\_account\_id} = :acc\_id) \\
&- \sum \text{investment\_transaction.settlement\_amount} \quad (\text{條件: } \text{settlement\_account\_id} = :acc\_id \text{ 且類別為 } \text{buy}) \\
&+ \sum \text{investment\_transaction.settlement\_amount} \quad (\text{條件: } \text{settlement\_account\_id} = :acc\_id \text{ 且類別為 } \text{sell})
\end{aligned}$$

> **重要備註**：
> - 現金股利（`cash_dividend`）與減資退回之現金金流，已於 `income` 表中作為入帳列登記，故其對帳戶餘額之增益已自動包含於 $\sum \text{income.amount}$，不在此處重複計算交割金額，以防止雙重計入。
> - 信用卡帳戶之餘額通常呈現負值或欠款狀態，消費時負債增加，透過 `transfer` 自銀行轉帳繳款時負債沖銷。

---

### 3.2 投資標的持有股數與平均成本推導邏輯

針對指定投資標的（`target_id = :tgt_id`），截至特定時間點的持有股數與平均成本，由 `investment_transaction` 歷史交易序列由早至晚按時間軸迭代計算。

#### (1) 持有股數（Shares Held）計算公式
$$\begin{aligned}
\text{持有股數} = &\ \sum \text{shares}_{\text{buy}} \\
&+ \sum \text{shares}_{\text{stock\_dividend}} \\
&+ \sum \text{shares}_{\text{reinvest}} \\
&+ \sum \text{shares變動}_{\text{split}} \\
&- \sum \text{shares}_{\text{sell}} \\
&- \sum \text{shares變動}_{\text{reverse\_split}} \\
&- \sum \text{shares變動}_{\text{capital\_reduction}}
\end{aligned}$$

#### (2) 平均成本（Average Cost per Share）迭代計算規則
系統採用移動加權平均法（Moving Weighted Average Cost Method）：

1. **買進（`buy`）與股息再投入（`reinvest`）**：
   - 新總持股成本 = 前期總持股成本 + （本次成交單價 $\times$ 本次股數）+ 手續費。
   - 新持有股數 = 前期持股股數 + 本次股數。
   - 新平均每股成本 = 新總持股成本 $\div$ 新持有股數。
2. **賣出（`sell`）**：
   - 平均每股成本保持不變。
   - 總持股成本依比例扣減：新總持股成本 = 前期總持股成本 $-$（本次賣出股數 $\times$ 前期平均每股成本）。
   - 新持有股數 = 前期持股股數 $-$ 本次賣出股數。
3. **配股（`stock_dividend`，股票股利）**：
   - 總持股成本不變（無新金流投入）。
   - 新持有股數 = 前期持股股數 + 本次獲配股數。
   - 新平均每股成本 = 前期總持股成本 $\div$ 新持有股數（每股成本稀釋下降）。
4. **股票分割（`split`）與股票合併（`reverse_split`）**：
   - 總持股成本不變。
   - 分割後股數 = 前期持股股數 $\times \text{ratio}$；合併後股數 = 前期持股股數 $\times \text{ratio}$（$\text{ratio} < 1$）。
   - 新平均每股成本 = 前期總持股成本 $\div$ 新持有股數。
5. **減資（`capital_reduction`）**：
   - 若為彌補虧損減資：總成本不變，持有股數依減資比例銷除，每股成本相應提高。
   - 若為現金減資退還股款：新總持股成本 = 前期總持股成本 $-$ 退還現金總額；新持有股數依減資比例減少；新平均每股成本 = 新總持股成本 $\div$ 剩餘股數。
6. **現金股利（`cash_dividend`）**：
   - 股數不變；現金款項認列為收益進帳（獨立列於 `income` 表），不影響持股股數。

## 4. 統一發票開獎與期別運算規則

### 4.1 開立日期換算開獎期別精確演算法
台灣統一發票對獎每兩個月為一期（逢單月開出前兩個月雙月之獎項）。發票開立日（`issue_date`）決定其所屬開獎期別（`period`）。

#### 決定規則與演算法
設開立日期之西元年分為 $Y$，月份為 $M \in \{1, 2, \dots, 12\}$：
1. 計算期別月份 $P_M$：
   $$P_M = \lceil \frac{M}{2} \rceil \times 2$$
2. 若 $P_M < 10$，於十位數補 `0`。
3. 期別字串格式化為：`YYYY-MM`（其中 `YYYY` 為 $Y$，`MM` 為補零後之 $P_M$）。

#### 月份與期別對照表
| 開立月份（$M$） | 俗稱期別名稱 | 期別代碼（`period` 欄位值） | 對應開獎時間 |
| :---: | :---: | :---: | :---: |
| 1 月 或 2 月 | 1 - 2 月期（第 1 期） | `YYYY-02` | 該年 3 月 25 日開獎 |
| 3 月 或 4 月 | 3 - 4 月期（第 2 期） | `YYYY-04` | 該年 5 月 25 日開獎 |
| 5 月 或 6 月 | 5 - 6 月期（第 3 期） | `YYYY-06` | 該年 7 月 25 日開獎 |
| 7 月 或 8 月 | 7 - 8 月期（第 4 期） | `YYYY-08` | 該年 9 月 25 日開獎 |
| 9 月 或 10 月 | 9 - 10 月期（第 5 期） | `YYYY-10` | 該年 11 月 25 日開獎 |
| 11 月 或 12 月 | 11 - 12 月期（第 6 期） | `YYYY-12` | 次年 1 月 25 日開獎 |

**實施位置**：由 API 在將發票資料寫入或更新至 `invoice` 表前執行此運算，將產生的期別字串填入 `invoice.period` 欄位。

## 5. 跨表連動與規則實施位置對照表

系統所有商業邏輯規則，精確劃分為「PostgreSQL 資料庫約束」與「由 API 在寫入前檢查」兩大類：

| 規則項目 | 業務意義說明 | 實施機制與位置 |
| :--- | :--- | :--- |
| **主鍵不可變整數** | 每張表的主鍵一旦建立即不可修改 | **PostgreSQL 約束**（`IDENTITY` 主鍵，禁止更新） |
| **預設防刪保護** | 被引用的父列不可被刪除（如帳戶被花費參照） | **PostgreSQL 約束**（`ON DELETE RESTRICT`） |
| **發票品項連帶消失** | 發票刪除時，附屬品項明細隨之刪除 | **PostgreSQL 約束**（`ON DELETE CASCADE`，唯一例外） |
| **審計時間戳記** | 記錄建立與最後更新時間 | **PostgreSQL**：`created_at DEFAULT (now() AT TIME ZONE 'utc')`<br>**由 API 在寫入前檢查**：`updated_at` 由程式更新寫入 |
| **分類名稱唯一性** | 入帳分類與花費分類分開，名稱各自不得重複 | **PostgreSQL 約束**（各自表設定 `UNIQUE (name)`） |
| **台幣匯率固定為 1** | 台幣交易匯率必須為 1.0，外幣匯率大於 0 | **PostgreSQL 約束**（`CHECK` 條件式約束） |
| **發票格式驗證** | 統一發票號碼必須為 2 碼大寫英文字母接續 8 碼數字 | **PostgreSQL 約束**（`CHECK (invoice_number ~ '^[A-Z]{2}[0-9]{8}$')`） |
| **發票期別唯一性** | 同一期別內同一發票號碼只能登錄一次 | **PostgreSQL 約束**（`UNIQUE (period, invoice_number)`） |
| **發票中獎單筆入帳** | 一張發票最多只能產生一筆入帳 | **PostgreSQL 約束**（`income.invoice_id` 設定 `UNIQUE`） |
| **投資交易單筆入帳** | 現金股利或減資交易最多只能產生一筆入帳 | **PostgreSQL 約束**（`income.investment_transaction_id` 設定 `UNIQUE`） |
| **開立日換算期別** | 發票期別根據開立日期雙月原則自動產生 | **由 API 在寫入前檢查**（API 計算後寫入 `invoice.period`） |
| **賣出不得使持股小於 0** | 賣出交易股數不得超過截至當下累計持有股數 | **由 API 在寫入前檢查**（API 於資料庫交易內鎖定並檢核持股數） |
| **開獎獎金資料驅動** | 對獎獎金來自資料庫，不寫死於程式碼 | **PostgreSQL 約束**（存於 `invoice_lottery_prize.prize_amount`） |
| **發票花費多對一** | 一張發票對到多筆花費，金額總和不強制等於發票總額 | **由 API 在寫入前檢查**（允許多筆花費指向同發票，不設等於約束） |

## 6. 這一次不建的表

依據專案核心需求與範圍限制，為保持個人記帳本核心結構純粹，以下功能模組與關聯資料表**本次明確不予建立**：

1. **預算表（`budget` / `budget_category`）**
   - 不建原因：本階段專注於記帳事實之忠實記錄，尚不需要設定每月支出限額或預算超支告警。
2. **固定收支表（`recurring_transaction` / `scheduled_expense`）**
   - 不建原因：租金、定期訂閱費、固定扣繳等定期任務，暫不使用排程樣板自動產生，目前所有帳務均由手動核實記帳。
3. **載具自動匯入記錄表（`carrier_invoice_sync` / `einvoice_carrier`）**
   - 不建原因：暫不介接財政部電子發票整合服務平台之手機條碼載具 API，發票留底由個人手動輸入或後續單筆匯入。
4. **即時股價與報價快取表（`realtime_stock_quote` / `market_price`）**
   - 不建原因：系統僅記錄買賣交易歷史與持有成本，不串接即時或延遲證券行情 API，不在此階段進行未實現損益與市價浮動試算。
5. **銀行同步設定與日誌表（`bank_sync_connection` / `bank_sync_log`）**
   - 不建原因：不整合 Open Banking、開放 API 或網銀爬蟲自動同步金流，所有帳戶收支與移轉由使用者手動維護。
6. **複式記帳會計分錄表（`journal_entry` / `ledger_entry`）**
   - 不建原因：避免會計借貸平衡與複雜分錄機制帶來的使用門檻，採用單式帳務結構配合專門的 `transfer` 表，即能清楚呈現個人現金流與帳戶資產變化。
7. **刪除記帳列 / 軟刪除審計表（`soft_delete_audit` / `transaction_recycle_bin`）**
   - 不建原因：系統原則為「不刪除帳務列」，帳務一經成立若有誤記，應以相反記帳（紅字沖銷）或修正方式處理，不建立軟刪除旗標或回收站結構。
8. **使用者帳號與家庭共享表（`user` / `family_share` / `permission`）**
   - 不建原因：本系統為完全給自己一人使用的私有記帳本，不支援多租戶、會員登入系統或多人協同帳本。
